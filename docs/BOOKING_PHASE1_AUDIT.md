# Booking Phase 1 audit and architecture proposal

Audit date: 2026-10-09 (Asia/Saigon). Scope: **STEP 1 ONLY** across `Neotek Frontend` and `Neotek Backend`. Paths below are relative to the named checkout. This document is a proposal, not an implemented feature or migration. No application source, schema, infrastructure, credentials, or database records were changed.

## Review checkpoint

**Stop after this audit.** Customer identity isolation has a clear recommendation, but reservation policy and calendar capacity materially determine the database constraint. Approve those decisions before implementing the schema. No deployment, commit, push, database reset, `db push`, Google integration, SMS, or Docker/DNS changes are included.

Recommended architecture:

- Separate `CustomerAccount` identity, customer sessions, CSRF tokens, guards and frontend provider from the existing CMS `User`/ADMIN/EDITOR system.
- PostgreSQL-owned Booking, append-only events, internal notes and durable notification deliveries. Redis remains session/rate-limit infrastructure, never the booking source of truth.
- Reuse the existing custom React calendar and Radix booking dialog; replace mock data and local success with an API-backed flow. Authentication starts at confirmation.
- Use a resource-scoped PostgreSQL exclusion constraint for overlapping reservations, with a required resource even for a single shared calendar.
- Recommend `PENDING` reserves capacity until an operator confirms/cancels. This needs business approval and anti-abuse limits; expiry is not silently assumed.
- Keep future calendar/meeting state in a separate optional `BookingIntegration` model, with no vendor implementation in Phase 1.
- Booking creation/status change and notification enqueue occur in one transaction. Sending occurs after commit through `NotificationService -> EmailProvider`.

## 8. Security risks and controls to preserve

### Verified current foundation

Backend `UserRole` only contains ADMIN/EDITOR. Admin session tokens are random 32-byte opaque values; Redis stores them under SHA-256-keyed `auth:session:*`, fixed eight-hour TTL. Every authenticated lookup rechecks the database user's current role and active state. Argon2id hashing and a dummy hash for unknown-user login are implemented in `password.util.ts`/`auth.service.ts`.

Production cookie is `__Host-neotek_admin_session` (HttpOnly, Secure, SameSite=Lax, path `/`, no Domain). Admin CSRF uses `neotek_admin_csrf`, header `x-csrf-token`, constant-time server comparison and atomic session-bounded Redis token creation/reuse. Invalid CSRF is 403; missing/expired sessions 401; session storage errors 500. Redis rate limiting fails closed with 503 on dependency failure. Login limits cover hashed IP and normalized email; mutations/media/CSRF have their own buckets.

`OriginGuard` requires an exact `FRONTEND_URL` match, including rejecting absent Origin. `http-security.ts` preserves Helmet, explicit proxy trust, credentials CORS, 2 MB JSON/64 KB urlencoded limits, safe error responses, request IDs/redacted logs, no-store on `/api/auth|admin|users`, bounded shutdown behavior. Production environment validation enforces exact HTTPS frontend origin and explicit proxy IP/CIDR entries. There is no global class-validator ValidationPipe: CMS uses strict Zod and endpoint-specific checks. TypeScript DTO classes alone do not validate input.

CMS public retrieval rechecks PUBLISHED state at the database boundary even on cache hits; page cache invalidation targets exact `cms:page:<slug>:<locale>` keys. Preserve these behaviors and existing ADMIN-only structural restrictions.

### New boundaries and risks

1. Never add customers to `User` with its default EDITOR role or reuse CMS cookies/guards. Identity isolation is mandatory on the server as well as in React.
2. Customer booking detail queries must include both booking ID and authenticated customer ID. Return 404 for another customer's ID. Never accept client `customerId`.
3. Strict Zod schemas reject unknown keys, including status, assignment, notes, integration IDs, meeting URL, version/audit timestamps. Plain text only; escape output and email templates. Bound query ranges, pagination/search lengths and all contact fields.
4. Add no-store coverage for `/api/customer/*` and authenticated `/api/bookings*`; use explicit DTO projections for public/customer/admin responses. Never return raw Prisma entities or internal event/note data to customers.
5. Anonymous availability should expose only start/end/available, not names, emails, phone/company, booking IDs, reasons, staff notes or per-booking labels. Merge overlapping/adjacent unavailable periods before projection; do not expose booking counts through availability metadata.
6. Preserve exact Origin for login/register; customer CSRF guards for authenticated mutations/logout. Reuse hashing/Redis primitives, not admin-bound guard classes. Customer CSRF cookies and tokens must be distinct.
7. Customer login/register quotas need separate namespaces with IP/account limits, mutation quotas per customer/IP and a server-side cap on active future reservations. Decide email verification before enabling unrestricted reservation; registration alone does not establish email ownership.
8. Do not claim duplicate registration is enumeration-free if new accounts receive a cookie while duplicates receive a different result. Choose a generic verification-based flow for stronger privacy, or document the limited disclosure of an immediate-login registration flow. Invalid login remains generic with dummy-hash timing treatment.
9. Validate future dates, interval ordering/duration, scheduling horizon/lead time, supported timezone and operating hours on the server. A calendar click is not authorization or a reservation.
10. Pending intent must contain only bounded slot/solution data with TTL; never password/session tokens/contact drafts in URLs or localStorage. Validate return routes against a same-origin allowlist to prevent open redirects.
11. Treat notification payloads as PII: no passwords/tokens, redact errors, restrict operator access and define retention. Provider credentials remain backend-only. Email links point to authenticated account detail; do not email internal notes.

## 10. Proposed Booking domain and schema additions

The following is a **proposed additive Prisma schema diff expressed as additions**, not a change to `schema.prisma`. Names/limits are reviewable recommendations. Resource capacity and pending semantics remain gated. All relations/fields below are new except three inverse relation additions to User. Do not generate/apply a migration from this document yet.

```prisma
enum BookingStatus {
  PENDING
  CONFIRMED
  COMPLETED
  CANCELLED
  NO_SHOW
}

enum BookingEventType {
  CREATED
  STATUS_CHANGED
  NOTE_ADDED
}

enum NotificationStatus {
  PENDING
  PROCESSING
  SENT
  FAILED
}

model CustomerAccount {
  id            String    @id @default(cuid())
  email         String    @unique @db.VarChar(254)
  passwordHash  String
  name          String    @db.VarChar(120)
  phone         String?   @db.VarChar(32)
  company       String?   @db.VarChar(160)
  active        Boolean   @default(true)
  emailVerifiedAt DateTime? @db.Timestamptz(3)
  lastLoginAt   DateTime?  @db.Timestamptz(3)
  createdAt     DateTime  @default(now()) @db.Timestamptz(3)
  updatedAt     DateTime  @updatedAt @db.Timestamptz(3)
  bookings      Booking[]
}

model BookingResource {
  id        String    @id @default(cuid())
  key       String    @unique @db.VarChar(80)
  active    Boolean   @default(true)
  bookings  Booking[]
}

model Booking {
  id                  String          @id @default(cuid())
  customerId          String
  resourceId          String
  assignedUserId      String?
  contactName         String          @db.VarChar(120)
  contactEmail        String          @db.VarChar(254)
  contactPhone        String?         @db.VarChar(32)
  contactCompany      String?         @db.VarChar(160)
  customerMessage     String?         @db.VarChar(2000)
  moduleKey           String?         @db.VarChar(120)
  solutionLabel       String          @db.VarChar(240)
  locale              String          @db.VarChar(2)
  requestedStartAt    DateTime        @db.Timestamptz(3)
  requestedEndAt      DateTime        @db.Timestamptz(3)
  timezone            String          @db.VarChar(80)
  status              BookingStatus   @default(PENDING)
  version             Int             @default(1)
  idempotencyKey      String          @db.VarChar(80)
  requestFingerprint  String          @db.VarChar(64)
  confirmedAt         DateTime?       @db.Timestamptz(3)
  cancelledAt         DateTime?       @db.Timestamptz(3)
  completedAt         DateTime?       @db.Timestamptz(3)
  createdAt           DateTime        @default(now()) @db.Timestamptz(3)
  updatedAt           DateTime        @updatedAt @db.Timestamptz(3)

  resource            BookingResource @relation(fields: [resourceId], references: [id], onDelete: Restrict)

  notifications       NotificationDelivery[]

  @@unique([customerId, idempotencyKey])
  @@index([customerId, requestedStartAt, id])
  @@index([status, requestedStartAt, id])
  @@index([requestedStartAt])
  @@index([createdAt, id])
  @@index([assignedUserId, requestedStartAt])
}

model BookingEvent {
  id             String           @id @default(cuid())
  bookingId      String
  sequence       Int
  type           BookingEventType

  toStatus       BookingStatus?
  actorUserId    String?
  reason         String?          @db.VarChar(1000)
  createdAt      DateTime         @default(now()) @db.Timestamptz(3)
  booking        Booking          @relation(fields: [bookingId], references: [id], onDelete: Restrict)

  deliveries     NotificationDelivery[]

  @@unique([bookingId, sequence])
}

model BookingNote {
  id           String   @id @default(cuid())
  bookingId    String
  authorUserId String
  text         String   @db.VarChar(2000)
  createdAt    DateTime @default(now()) @db.Timestamptz(3)
  booking      Booking  @relation(fields: [bookingId], references: [id], onDelete: Restrict)
  author       User     @relation("BookingNoteAuthors", fields: [authorUserId], references: [id], onDelete: Restrict)

  @@index([bookingId, createdAt, id])
}

model NotificationDelivery {
  id                String             @id @default(cuid())
  bookingId         String
  eventId           String
  template          String             @db.VarChar(80)
  recipient         String             @db.VarChar(254)
  locale            String             @db.VarChar(2)
  payload           Json
  status            NotificationStatus @default(PENDING)
  attempts          Int                @default(0)
  nextAttemptAt     DateTime           @default(now()) @db.Timestamptz(3)
  lockedAt          DateTime?          @db.Timestamptz(3)
  lockToken         String?
  sentAt            DateTime?          @db.Timestamptz(3)
  lastErrorCode     String?            @db.VarChar(80)
  providerMessageId String?
  createdAt         DateTime           @default(now()) @db.Timestamptz(3)
  booking           Booking            @relation(fields: [bookingId], references: [id], onDelete: Restrict)
  event             BookingEvent       @relation(fields: [eventId], references: [id], onDelete: Restrict)

  @@index([status, nextAttemptAt])
  @@index([bookingId, createdAt])

```

Add inverse fields to existing User, without changing identity/role fields:

```prisma
assignedBookings Booking[]      @relation("AssignedBookings")
bookingEvents    BookingEvent[] @relation("BookingEventActors")
bookingNotes     BookingNote[]  @relation("BookingNoteAuthors")
```

Normalize customer email on write (trim/lowercase, matching login lookup) and add a database CHECK that persisted email equals its normalized form so the unique index also protects case variants. Booking contactEmail is **not unique**; default it to the authenticated account's verified address for notifications. Changing contact data never changes ownership. Booking snapshot preserves contact/solution details even when profile/catalogue changes. Prefer account deactivation over hard deletion; retention/anonymization is a separate explicit policy. Assignment is an admin-only optional foundation, not a capacity key or a new staff scheduling UI. New timestamps and version increments are server-owned.

Events are internal append-only records: CREATED uses the booking's customer relation as actor; STATUS_CHANGED/NOTE_ADDED require an admin actor. Increment Booking.version and assign the new value to event.sequence in the same transaction, including notes. Add SQL checks for actor/type and from/to consistency. No event/note editing/deletion API in V1. Customer-facing timeline, if later desired, requires a separate sanitized projection.

Index review: customer/time supports ownership/upcoming history; status/time supports admin filters; createdAt supports newest-first; start supports global date filters; assignment index is justified only if assignment queries ship. Avoid speculative GIN/full-text indexes until actual search performance requires them. Bounded admin search can initially use parameterized Prisma contact-field predicates with pagination. Verify plans on representative data before release.

### Status workflow

| From | Allowed target | Rule |
| --- | --- | --- |
| PENDING | CONFIRMED, CANCELLED | Admin action; confirmation before start; cancellation reason required |
| CONFIRMED | COMPLETED, NO_SHOW, CANCELLED | COMPLETED after end; NO_SHOW after agreed operational cutoff; cancellation reason required |
| COMPLETED, NO_SHOW, CANCELLED | None | Terminal in V1; no reopening/rescheduling shortcut |

Do not add CONTACTED without an operational need. Customers have read-only history; no cancellation/status API in V1. Recommend ADMIN-only Booking PII access/actions initially; EDITOR remains a CMS role until explicit Booking permission is approved. A status command validates transition, timing, expected version, current identity/permission and any capacity implication inside a transaction. Stale version returns 409 without duplicate events/emails. Duplicate/retried identical commands must not emit a second transition notification.

### Availability and concurrency strategy

Define server-owned scheduling policy (timezone, hours/days, holidays, lead time, horizon, durations, buffers). Public availability and creation share one policy implementation. Policy changes must serialize with creation (e.g. resource row lock/version) if editable at runtime. V1 can use reviewed backend configuration without adding a schedule editor. Do not treat absence of bookings outside working hours as availability.

Proposed non-null BookingResource scopes capacity; one resource per independently bookable capacity unit. Seed only a reviewed default shared resource for V1. Server resolves the resource; customers cannot submit arbitrary resource/staff IDs. A nullable assignment field cannot enforce capacity: unassigned bookings would evade equality-based constraints.

For approved PENDING-reserves policy, add this **custom migration SQL proposal** alongside the additive Prisma migration:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "Booking"
  ADD CONSTRAINT "Booking_valid_interval"
  CHECK ("requestedEndAt" > "requestedStartAt");

ALTER TABLE "Booking"
  ADD CONSTRAINT "Booking_resource_no_overlap"
  EXCLUDE USING gist (
    "resourceId" WITH =,
    tstzrange("requestedStartAt", "requestedEndAt", '[)') WITH &&
  ) WHERE ("status" IN ('PENDING', 'CONFIRMED', 'COMPLETED', 'NO_SHOW'));
```

Half-open intervals permit adjacency. Retaining COMPLETED/NO_SHOW in the constraint preserves historical occupied periods; cancellation releases capacity. Never use `now()` in a partial constraint predicate to implement expiry; an explicit transactional status update must release the slot. PENDING expiry, if approved, needs a documented deadline/worker and matching availability/creation semantics.

Creation transaction: validate customer/policy/catalogue and interval; resolve active resource; create Booking(PENDING), CREATED event and admin/customer notification delivery rows atomically. PostgreSQL rejects conflicting inserts/updates even when two requests both observed availability. Map the exclusion violation (SQLSTATE 23P01, actual Prisma 6.19 error wrapping to be tested) to safe 409. Do not leak the conflicting row. Idempotency is customer-scoped with a fingerprint of normalized request data: same key/body returns the committed booking; same key/different body returns 409. Handle unique-key and exclusion races without swallowing unrelated database errors.

Compare alternatives: a unique start-time index misses partial overlaps and variable durations; Redis locks are not a database invariant; check-then-insert without locking is unsafe. Serializable transactions with bounded retry or explicit per-resource locking can work, but the exclusion constraint is the clearest enduring DB guarantee for this interval model. If `btree_gist` is unavailable, stop and review a concrete alternative; do not downgrade to an unprotected insert.

PostgreSQL documents resource/range exclusion using GiST and `btree_gist`; this proposal adapts that mechanism to Booking. See [PostgreSQL range constraints](https://www.postgresql.org/docs/18/rangetypes.html#RANGETYPES-CONSTRAINT). Prisma 6 requires custom SQL for database features absent from its schema language; preserve that SQL in migration history and verify it after future migrations: [Prisma 6 unsupported-feature migrations](https://docs.prisma.io/docs/orm/v6/prisma-migrate/workflows/unsupported-database-features). These are design references, not evidence of the deployed database version.

### Future integration state

Option A puts nullable calendar/meeting fields on Booking: fewer joins but mixes reservation truth with vendor retry/state and becomes awkward for multiple targets. **Recommend B: optional BookingIntegration**, added in Phase 2 unless a concrete Phase 1 consumer appears. Conceptual fields: id, bookingId FK, integrationKey, calendarProvider, externalCalendarId, externalCalendarEventId, calendarSyncStatus, meetingProvider, externalMeetingId, meetingUrl, lastSyncedAt, lastErrorCode, timestamps; unique `(bookingId, integrationKey)` plus provider/calendar/event uniqueness where defined. No Google-specific names, credentials or vendor SDK in domain models.

The customer Booking DTO may expose `meetingUrl: null` in Phase 1 without storing a meaningless row. Later provider state stays optional and cannot override DB ownership/status. Phase 2 must define external busy-period import/conflict reconciliation explicitly; creating this model alone does not provide external calendar synchronization.

### Email architecture

BookingService coordinates the transaction; NotificationService enqueues typed deliveries using that same transaction; an EmailProvider implementation sends after commit. Persist creation notifications for admin and customer, and customer notifications for confirmation/cancellation. Internal notes do not trigger customer emails. Templates are escaped, locale-specific, bounded, and contain authenticated account links.

Use backend-only `EMAIL_PROVIDER`, `EMAIL_FROM`, `EMAIL_REPLY_TO`, provider-specific secrets, and a reviewed `BOOKING_ADMIN_EMAIL` destination. Development may use a fake/capture provider; it must be clearly labelled and rejected as production delivery. Provider/company credential changes require configuration only. Vendor selection and verified sender/domain are pending; no account configuration is performed here.

Durable NotificationDelivery is the outbox, not merely an in-memory callback. A bounded background dispatcher in the existing Nest process can claim due rows transactionally using row locks/SKIP LOCKED, assign a lease/token, send outside the transaction, then mark SENT or schedule bounded backoff. Reclaim expired leases after a crash; guard completion by lockToken. Cap attempts and expose redacted FAILED status in admin detail/operator logs, with a controlled retry path. No new deployment service is required for the proposal. Delivery is at least once: use provider idempotency if available; SMTP alone cannot guarantee exactly once after a send/ack crash. Database enqueue failure rolls back the creation transaction; provider send failure after commit never removes/rolls back Booking.

## 11. Proposed Customer Identity architecture

| Option | Assessment |
| --- | --- |
| A: extend User and UserRole | Reuses account plumbing but default EDITOR and admin-oriented `/auth` session/guards create escalation and lifecycle risks; changes every role/session consumer and complicates CRM customers versus CMS operators |
| B: separate CustomerAccount | Extra thin domain/session orchestration, but explicit table/ownership/guard boundaries; customer lifecycle and future CRM can evolve without rewriting CMS identities |

**Choose B for the proposal.** Do not alter UserRole or migrate existing operators. Same normalized email may intentionally exist in both tables, representing distinct accounts/passwords; no automatic linking or privilege inheritance. A future CRM contact can link to CustomerAccount without making a lead a login-capable CMS user.

Customer cookie: production `__Host-neotek_customer_session`, dev `neotek_customer_session`, HttpOnly, Secure under the existing production/local-development rules, path `/`, no Domain, SameSite=Lax. Recommend fixed eight-hour absolute TTL for V1, no remember-me until explicitly designed. Redis keys: `customer:session:<sha256>`, `customer:csrf:<sha256>`, `customer:ratelimit:<bucket>:<hash>`. Session payload contains explicit customer realm/customerId and server timestamps, no CMS role. Recheck active customer on requests. Regenerate token on login, atomically bind/reuse CSRF token within session TTL, revoke only customer session/CSRF on customer logout.

CustomerSessionGuard attaches `request.customer`; current SessionAuthGuard continues attaching `request.user`. CustomerCsrfGuard reads only customer cookies/keys. An admin cookie alone does not authenticate a customer API; a customer cookie alone does not authenticate CMS. If both sessions exist, each route uses only its own realm. Token swapping across cookie names must still fail because store namespaces are distinct. Shared primitives can be extracted narrowly, but replacing the working CMS auth service is unnecessary.

| POST `/api/bookings` | Customer session, CSRF, exact Origin, mutation quota; create transaction; 201 on new booking, documented replay response for idempotent retry, 409 on conflict |
| GET `/api/customer/bookings?scope=upcoming\|past&cursor=&limit=` | Own bookings only; bounded cursor pagination and deterministic time/id ordering; server defines upcoming/past from requestedEndAt and current time |

Proposed booking body: `requestedStartAt`, `requestedEndAt`, `timezone`, `moduleKey?`, `locale`, `contactName`, optional `contactPhone`, `contactCompany`, `customerMessage`, `idempotencyKey`. The server derives contactEmail/customerId/resourceId/solutionLabel and all operational fields. ISO timestamps require offsets; timezone must match the approved scheduling policy and conversion. Use the existing UI limits (name120/phone32/company160/message2000) as upper bounds; confirm required phone/company separately. Set a small booking/auth-specific body limit (e.g.16 KB) without weakening existing CMS parser contracts.

Register result/session semantics depend on the verification choice: immediate authenticated registration versus generic accepted/verification. Define that contract before frontend implementation. If verification is chosen, add separate bounded single-use verification token storage/endpoints/email templates in the reviewed schema; the illustrative additions above do not implement that flow.
